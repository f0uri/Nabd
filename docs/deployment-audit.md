# تشخيص «أنت في أحدث نسخة» وتكوين تلغرام — 2026-11-01

## شنو تفحص فعلياً؟

المقارنة المحلية وحدها ما كانتش كافية. تدار فحص داخل GitHub، باستعمال توكن Actions الموجود، بلا طلب مفاتيح من المستخدم وبلا عرض قيمها. الفحص نزل APK الأصلي داخل runner مؤقت، قرأ `assets/fingerprint`، قارن مصادر بصمته من سجل البناء، واستعلم عن قناة Expo وتحديثاتها. ما تبدلت حتى رسالة أو حساب في تلغرام.

الأدلة: [الفحص الأول](https://github.com/f0uri/Nabd/actions/runs/41291776558)، [مقارنة المصادر](https://github.com/f0uri/Nabd/actions/runs/41291934911)، [فحص البناء والبيئات](https://github.com/f0uri/Nabd/actions/runs/41292707470). النتائج المختصرة موجودة في annotations، بلا توكن أو معرف محادثة.

|---|---|
| قناة Expo `production` | موجودة، نشطة، مرتبطة بفرع `production` |
| runtime لتحديثات Android المنشورة | `218a8b15ac41835207e2125ecc9ee2f046f3fec2` |
| runtime داخل APK الأصلي، run `41267667174` | `5af5c2ccf709c41ea5c3bb99c0308f72ea7827be` |

| مصدر الاختلاف عن fingerprint النظيف | فقط `node_modules/expo-updates/expo-updates-gradle-plugin`، حسب مقارنة مصادر السجلات |
| fingerprint المحلي قبل/بعد prebuild | نفس `218a…`؛ لذلك نجاح المقارنة المحلية السابقة ما كانش دليلًا على بصمة APK المجمّع |
| تجربة Gradle `help` ثم إعادة الفحص | رجعت `218a…` بعد انتهاء الأمر؛ **ما حددناش اسم الملف المؤقت داخل plugin أثناء تجميع APK** |

**السبب المؤكد لعدم وصول OTA هو اختلاف runtime في APK الموزع عن runtime المنشور.** لا نحذف فحص التوافق ولا نعيد تسمية تحديث لبصمة قديمة بشكل أعمى. الاختلاف المرصود محدود بمصدر Gradle plugin أثناء البناء؛ ما كاينش دليل هنا على إضافة مكتبة أصلية في كود ميزة تلغرام.

## الإصلاح المضاف

1. بعد `expo prebuild` وقبل Gradle، `capture-android-runtime.cjs` يحسب fingerprint عبر resolver ديال `expo-updates` في وضع managed، ويتحقق أن السياسة ما زالت `fingerprint`.
2. يمرر القيمة المحسوبة إلى **hook الرسمي** `EXPO_UPDATES_FINGERPRINT_OVERRIDE` ديال بناء expo-updates. ما كاين حتى hash ثابت أو تغيير لسياسة runtime في `app.config.js`.
3. بعد تجميع APK، `verify-apk-runtime.cjs` يقرأ `assets/fingerprint` من APK نفسه، ويقارنه بالقيمة المحسوبة وبمصادر المشروع بعد البناء. أي اختلاف يوقف رفع artifact بدل إصدار APK ما كيستقبلش OTA المنشور.
4. واجهة التحديث ما بقاتش تعتبر كل `isAvailable=false` دليلاً على «أحدث إصدار». كتفرّق بين عدم وجود تحديث متوافق، رفضه بسياسة التوافق، وفشل تشغيل سابق. كتبيّن runtime/channel/update ID ومصدر البيانات بلا أسرار.

الاختبارات المحلية تثبت وصول القيمة إلى hook الرسمي ورفض ZIP تجريبي ببصمة خاطئة. **هذا ماشي بناء Android أصلي كامل محليًا**؛ يلزم نجاح workflow الجديد وفحص APK الناتج قبل القول إن APK المصحح متاح.

### على الهاتف

APK القديم ما نقدرش نغيّر runtime دياله بتحديث JavaScript ما كيوصلوش أصلاً. المسار الآمن هو تثبيت APK مصحح مرة واحدة، من بناء يتجاوز خطوة التحقق الجديدة. ثبّتو فوق التطبيق الحالي إذا التوقيع مطابق؛ **ما تحذفش التطبيق ولا تمسح بياناته**. إذا Android رفض التثبيت، وقف وراجع التوقيع بدل حذف البيانات. بعدها تحديثات نفس runtime تقدر توصل بشكل عادي. التثبيت لا يهاجر حسابات GraphQL إلى JSON تلغرام.

## معلومات البوت: النطاق اللي تفحص

- GitHub integration المحلي ردّ `403` على لائحة variables/secrets، لذلك ما استنتجناش من هاد الرد أنها غير موجودة.
- runner الفعلي في **`f0uri/Nabd`** تلقّى mode=`auto`، وما تلقّى حتى قيمة تحت أسماء `NABD_TELEGRAM_BOT_TOKEN` أو `TELEGRAM_BOT_TOKEN` أو `EXPO_PUBLIC_TELEGRAM_BOT_TOKEN` من Secrets، ولا أسماء chat المعروفة من Variables/Secrets. لذلك هاد النشر **ما كيضمّنش إعداد تلغرام المباشر**.
- ما كاين حتى GitHub Environment معرف في Nabd وقت الفحص.
- الاستعلام عن metadata ديال EAS production على مستوى المشروع والحساب نجح، وما ظهر حتى اسم مطابق لتكوين البوت/المحادثة/مصدر البيانات المعروف. ما عرضنا حتى قيمة. هاد الفحص ماشي حكم على مستودع آخر أو خدمة خارجية أو اسم مختلف.
- المستودع وZIP الأصلي فيهما `.env.example` فارغة لتلغرام، وليس ملف إعداد Nabd بقيم فعلية. أسرار `ahdaf` ما تفكّاتش وما تنسخاتش وما استُعملاتش.

إذا المعلومات مسجلة في مكان آخر، خاص تحديد **اسم المكان أو اسم خانة الإعداد فقط** (مثل Nabd مقابل مستودع آخر)، بلا إرسال المفتاح في المحادثة. ما خاصش إعادة إنشاء بوت تلقائيًا أو نسخ بوت تطبيق آخر.

لمنع مشكلة اختلاف الأسماء، مسار البناء يقبل الآن الأسماء القديمة المعروفة بالإضافة إلى `NABD_*`، لكن **فقط مع اختيار `telegram` صراحة**. وجود توكن وحده ما كيبدلش مصدر البيانات تلقائيًا، وما كنضمّنوهش في بناء GraphQL/auto. راجع [إعداد تلغرام المباشر ومخاطره](telegram-hosting.md).

## فحص قابل للإعادة

Workflow **Read-only deployment audit** يعمل يدويًا أو عند تغيير ملفات التشخيص على main، وليس على PR، وبصلاحيات `contents:read` و`actions:read` فقط. `apk_run` يحدد APK المراد فحصه؛ `trace_gradle` اختيار إضافي بطيء، ما ينشرش أي نسخة. لا تمر أسرار تلغرام إلى اختبارات PR، ولا تُخزَّن ملفات حسابات Telegram في artifacts أو Git.
