# تسجيل الدخول والحسابات: التحسينات وحدود الأمان

## الواجهة

واجهة عربية متجاوبة للدخول والتسجيل، ببطاقة واضحة وحقول تركيز وأزرار لمس مناسبة، وإظهار/إخفاء كلمة المرور وملء تلقائي. الاسم مطلوب والصورة اختيارية، واليوزر المقترح يُشتق من الاسم؛ الاقتراح ليس حجزاً مسبقاً. يمكن تسجيل الدخول بالبريد أو اليوزر وتعديله من الملف الشخصي. أُزيلت عبارات الحسابات «الحقيقية/التجريبية» وتقنيات التطوير والتشبيه بفيسبوك من الواجهات العامة، مع الإبقاء على الأخطاء الحقيقية. أُزيلت لاحقاً شاشة تحذير تلغرام بطلب صريح من المالك، مع بقاء الحدود موثقة والتأكيد المنفصل عند إنشاء مساحة بيانات جديدة.

## الانتظار

- سابقاً: الجلسة المحفوظة تنتظر `me()` قبل السماح بعرض التطبيق. الآن تُعرض الجلسة المحفوظة فور قراءتها ويُحدَّث الحساب عن بعد؛ إن فشلت الشبكة تبقى الجلسة، وإن انتهت صلاحيتها تُزال. لا تمنح النسخة المحلية صلاحية كتابة؛ كل عملية ما زالت تتحقق من الجلسة لدى المصدر.
- الجلسات المتأخرة لا تعيد حساباً بعد الخروج أو بدء محاولة دخول أخرى. الضغط المتكرر لا ينشئ عمليات دخول/تسجيل متوازية، وفشل حفظ الجلسة لا يترك توكن خفياً نشطاً في النقل.
- في مسار تلغرام غير المتعارض انخفض تنزيل ملف الحسابات في الدخول من ثلاث مرات إلى مرتين: نعيد استخدام ملف Telegram غير القابل للتعديل **فقط بعد فحص الرسالة المثبتة الحية**. عند تغيرها نعيد التنزيل، ونراجع كلمة المرور مجدداً، وتبقى فحوص التعارض والتثبيت وقراءة تأكيد الحفظ.
- البريد المسجل يُرفض قبل حساب كلمة السر أو معالجة الصورة. معالجة الصورة والحساب تجريان بالتوازي بعد ذلك مع إعادة فحص البريد عند تحديث الملف.
- PBKDF2-SHA256 يبقى **210000 دورة** بنفس salt والنتيجة ودون تغيير حسابات قديمة. يُستخدم WebCrypto الموجود أصلاً إذا توفر؛ Hermes قد لا يوفّره، ولم نضف مكتبة أصلية. في المسار JavaScript عُدّل جدولة الخروج من PBKDF2 إلى event loop بدل microtasks فقط، لتستجيب الواجهة أثناء الحساب؛ **هذا لا يعني أن حساب كلمة المرور نفسه أصبح فورياً**.
- لا توجد أوقات انتظار وهمية أو نسب تقدم مصطنعة أو نجاح قبل تأكيد الحفظ. الشبكات البطيئة وحجم JSON وأداء الهاتف ما زالت تؤثر. يلزم قياس على الهاتف قبل الجزم باختفاء انتظار الدقيقة؛ الاختبارات المحلية ليست قياس Hermes على جهاز حقيقي.

## اليوزر

- تحويل ثابت للاسم إلى أحرف لاتينية صغيرة، مع تقريب الحروف العربية وإزالة علامات التشكيل، وأرقام لاحقة عند التكرار. يظل الاسم المعروض منفصلاً عن اليوزر، ولا تتغير اليوزرات الموجودة تلقائياً.
- التعديل يطبّع الحالة و`@` ويرفض الصيغ الخاطئة واليوزر المستعمل.
- GraphQL/PostgreSQL: الفهرس الفريد `lower(username)` هو الحكم عند التسجيل المتزامن، مع إعادة محاولة اسم مولّد آخر. هذه تغييرات خادم يلزم نشرها في خدمة GraphQL إن استُخدمت، ولا تُنشر بواسطة OTA.
- تلغرام المباشر: التحقق يتم من أحدث نسخة مرصودة وفحوص التعارض الموجودة؛ **لا يوجد حجز ذري عابر للأجهزة أو ضمان عدم فقد تحديث تحت كل حالات التزامن**. لا نغيّر بنية التخزين أو ننقل الحسابات تلقائياً، ولا ندّعي أن JSON أصبح قاعدة معاملات.

## طلب دخول الأدمن باسم مشفر دون كلمة سر

**لم نضف باباً خلفياً أو رمزاً ثابتاً داخل التطبيق.** الاسم، سواء بدا مشفراً أو كان `admin`، لا يمنح صلاحية. لوحة الإدارة لا تُعرض إلا لحساب يحمل دوراً مناسباً، والخادم يفرض `requireAdmin` لكل عملية إدارية؛ إخفاء الشاشة وحده ليس إجراء أمان.

تلغرام المباشر يعيد `isAdmin: false` عمداً، لأن التوكن المشترك وملف JSON القابل للقراءة والكتابة من العملاء لا يشكلان سلطة تحقق موثوقة. لا يمكن الادعاء بدخول أدمن «قوي ومؤمن» بمجرد مفتاح يتحقق منه كود الواجهة أو JSON نفسه. الحل يحتاج قراراً منفصلاً بمصدر تحقق موثوق، مثل رموز دخول عشوائية قصيرة العمر أحادية الاستخدام يتحقق منها خادم، أو passkeys. لم نضف خادماً/وسيطاً أو مكتبة أصلية دون موافقة، ولم نفعّل طريقة الأدمن المطلوبة على أنها آمنة.

## التحديث بدون تنزيل APK آخر

لم تتغير dependencies أو lockfile أو أيقونات أو إعدادات Expo أو أذونات Android. تم التحقق محلياً بمسار SDK الرسمي من بقاء runtime الحالي **890f4e94d21f5b3f036854a7836b1aecc00fb45b** قبل/بعد التغييرات.

لأصحاب APK تلغرام المصحح **قبل الأيقونة** أُضيف نشر cohort منفصل، مع نفس JavaScript الأحدث ولكن بإعداد الأيقونة الأصلي وقت تصدير OTA فقط:

1. `publish-legacy-update.cjs` يزيل حقلي الأيقونة الجديدين ويعيد خلفية adaptive الأصلية في نسخة إعداد مؤقتة.
2. يحسب Expo SDK البصمة الحقيقية بسياسة fingerprint، ويقارنها ببصمة APK المصحح المعروفة **218a8b15ac41835207e2125ecc9ee2f046f3fec2**.
3. هذا **تحقق allowlist وليس فرض runtime**؛ لا يُحقن hash في الإعداد أو البيئة. إذا تغيّرت مكتبة/صلاحية/تهيئة أخرى يتخطى النشر للنسخة القديمة، بدلاً من تحميل كود غير متوافق.
4. لا ينشر dry-run في PR أي شيء، ولا يستخدم أسراراً. النشر الفعلي محصور في وظيفة `publish` على main. الإعداد الأصلي يُستعاد في `finally` عند النجاح والفشل، وAPK يبقى بأيقونته الجديدة.
5. النشر الإضافي يخضع لحصص وخطة Expo نفسها، وليس استخداماً غير محدود. قناة production تستطيع حمل تحديثات متعددة ذات runtimes مختلفة؛ يختار Expo المتوافق مع APK. الأيقونة على شاشة هاتف مستخدم النسخة القديمة لن تتغير عبر OTA، لكن الواجهة البرمجية يمكن أن تتحدث.

هذا لا يستهدف APK المؤسس القديم ذي runtime `5af…` الذي كانت بصمته معطوبة، ولا يدّعي وصول التحديث إلى هاتف قبل نجاح النشر والفحص الفعلي عليه.
