# تشغيل نبض مؤقتًا مع تخزين تلغرام — للمستخدمين الحقيقيين

## الاختيار المنفّذ

بعد اختيار استخدام حسابات حقيقية، لا ننقل توكن بوت مشترك إلى الهاتف ولا ننسخ أسلوب `ahdaf` الذي يعيد كتابة ملف حسابات كامل من كل جهاز. نستعمل خادم نبض الموجود كوسيط، بلا واجهة وسيطة إضافية مكررة:

```text
الهاتف ── HTTPS /graphql ── خادم نبض ── Bot API ── قناة/محادثة خاصة
                                 │
                                 └── قاعدة الحسابات واليوزرات ومرجع file_id
الهاتف ◀── /media/:id ◀───────────┘
```

**تلغرام يخزّن الوسائط، وليس قاعدة الحسابات.** تبقى الحسابات وكلمات المرور المجزأة واليوزرات في PostgreSQL أو PGlite على قرص دائم، حفاظًا على تفرد اليوزر وعدم فقد التعديلات المتزامنة. ليست هذه طريقة لتشغيل الكود داخل تلغرام أو لإلغاء استضافة الوسيط.

الكود والإعدادات جاهزة للنشر، لكن لم تُنشأ استضافة، ولم تُستخدم بيانات بوت حقيقية، ولم تُدفع رسوم أو يُعدّل عنوان API للتطبيق. يلزم إكمال الخطوات أدناه قبل القول إن الحفظ السحابي مفعّل.

## خيار النشر من الهاتف: Render Blueprint

أُضيف `render.yaml` في جذر المستودع. يجهّز خدمة Docker واحدة على Node 22، وقرصًا دائمًا لـ PGlite والوسائط المحلية المرآتية، ويطلب أسرار تلغرام من لوحة الاستضافة. لا يحتاج PostgreSQL خارجيًا في هذا الخيار.

**تنبيه التكلفة:** الملف يطلب خطة `starter` وقرصًا دائمًا. قد تترتب عليهما رسوم حسب أسعار المزود الحالية. هذا ليس وعدًا باستضافة مجانية. راجع التكلفة المعروضة ووافق عليها بنفسك قبل إنشاء الخدمة. مجرد رفع/دمج الملف لا ينشئ حسابًا أو خدمة ولا يحمّل أي رسوم. يمكن استخدام استضافة أخرى تقبل Docker وقرصًا دائمًا بدلًا من Render.

1. بعد دمج طلب التعديل، اربط مستودع `f0uri/Nabd` بحساب الاستضافة واختر نشر Blueprint من `render.yaml` على `main`.
2. أنشئ **بوتًا منفصلًا لنبض** وقناة خاصة، وأضف البوت مشرفًا بصلاحية نشر المستندات. محادثة شخصية بدأتَ فيها البوت ممكنة كذلك. لا تستخدم قناة عامة لملفات المستخدمين.
3. في لوحة أسرار **خدمة الخادم** فقط، ضع:
   - `TELEGRAM_BOT_TOKEN`: توكن البوت.
   - `TELEGRAM_CHAT_ID`: معرّف القناة/المحادثة الخاصة.
   - ينشئ Blueprint قيمة `AUTH_SECRET` عشوائية. احفظها ثابتة بين النشرات. إذا كنت تنقل خادمًا موجودًا، احتفظ بسرّه الحالي القوي وقاعدة بياناته، ولا تنشئ قاعدة فارغة بدل بيانات المستخدمين.
4. احتفظ بالقرص المركّب عند `/app/data`. قاعدة PGlite في `/app/data/pg`، والوسائط المحلية المرآتية في `/app/data/uploads`. لا تزد عدد النسخ عن واحدة مع PGlite، ولا تحذف القرص عند إعادة النشر. خذ نسخًا احتياطية مستقلة؛ تلغرام لا يعوّض نسخة قاعدة البيانات.
5. ينفّذ الخادم عند الإقلاع فحص `getMe` و`getChat` قبل قبول المستخدمين. نقص الأسرار أو بطلان الوصول أو الوجهة العامة يوقفه بدل التخزين المحلي الصامت. الفحص لا يثبت صلاحية رفع المستندات؛ اختبر رفع صورة فعلية بعد التشغيل.
6. بعد نجاح الخدمة، احصل على عنوان HTTPS العام وافحص `/health`. ثم في **GitHub Actions repository variables**:
   - `NABD_API_URL=https://YOUR_REAL_HOST/graphql`
   - `NABD_DATA_SOURCE=graphql`
   لا تضع توكن تلغرام أو `AUTH_SECRET` في `EXPO_PUBLIC_*` أو GitHub Variables أو المحادثة. المفتاح `EXPO_TOKEN` الموجود لنشر OTA منفصل تمامًا عن أسرار الخادم.
7. شغّل **App updates (OTA)** على `main` ليُضمَّن عنوان API الحقيقي في JavaScript. يبقى مشروع Expo وقناة التحديث كما هما؛ لا تُضاف مكتبة أصلية أو صلاحية إلى APK.
8. اختبر من حسابين حقيقيين: تسجيل الدخول، يوزر مختلف مع اسم ظاهر مكرر، صورة ملف، إغلاق الهاتف وفتحه، ثم إعادة نشر الخادم والتأكد من بقاء الحسابات والصور. جلسات Mock السابقة ليست حسابات خادم، والصور التي لم تُرفع أصلًا يجب اختيارها مجددًا.

إذا استُخدم بوت كانت بياناته مضمّنة في تطبيق آخر، اعتبر التوكن مكشوفًا وبدّله من BotFather، ولا تنقله كما هو إلى نبض. لا تُنسخ أسرار `ahdaf` ولا بيانات مستخدميه.

## بديل Docker على استضافة موجودة

`server/docker-compose.yml` يشغّل الوسيط مع PostgreSQL وشبكة داخلية وقاعدة غير منشورة على بورت عام. يحتاج أسرارًا منفصلة عشوائية:

```sh
cd server
# املأ .env على الاستضافة نفسها، لا في المستودع أو المحادثة.
# AUTH_SECRET: قيمة عشوائية طويلة وثابتة (32 حرفًا على الأقل).
# POSTGRES_PASSWORD: قيمة عشوائية hex، وليست كلمة المرور القديمة المنشورة.
# TELEGRAM_BOT_TOKEN و TELEGRAM_CHAT_ID: أسرار الاستضافة فقط.
docker compose up -d --build
```

تحتاج أيضًا HTTPS أمام بورت API. إذا عندك PostgreSQL/volume موجود، خذ نسخة احتياطية وخطّط لترحيل كلمة المرور قبل تغييرها: متغير `POSTGRES_PASSWORD` لا يغيّر كلمة مرور قاعدة قديمة تلقائيًا. لا تحذف volume لكي تتجاوز خطأ الدخول.

ملف `.dockerignore` يمنع إدخال ملفات البيئة والجلسات والتوكنات والبيانات والوسائط المحلية و`node_modules` في صورة Docker. يستعمل البناء `npm ci` مع lockfile.

## ضوابط النسخة المؤقتة

- لا توكن بوت ولا رابط تنزيل يحتويه يُعاد للهاتف. أخطاء Telegram والشبكة تُحوّل إلى رموز ثابتة، وواجهة الوسائط لا تعيد التفاصيل الخام. لا يُعرض معرّف المحادثة في بيانات الصحة العامة.
- طلبات Telegram لا تتبع تحويلات HTTP، ولها مهلة. حد رفع الوسائط الجديد 18 MiB كسياسة للتطبيق؛ راجع حدود Bot API الحالية قبل رفعه. لا يُخزّن `file_id` إن لم تكن نتيجة الرفع مكتملة.
- الإنتاج يتطلب `AUTH_SECRET` قويًا، ولا يرقّي أول مستخدم عشوائي تلقائيًا إلى أدمن. لمنح الإدارة، أنشئ حساب المالك أولًا ثم اضبط `ADMIN_EMAILS` على بريده في أسرار الخادم وأعد تشغيله. تحقق من ملكية الحساب بنفسك؛ إثبات البريد الآلي ليس مضافًا هنا.
- واجهة GraphiQL التفاعلية مقفلة في الإنتاج، لكن introspection يبقى متاحًا لفحص توافق اليوزر. الكتابة في الملف تحتاج توكن دخول صالحًا.
- **هذا ليس تدقيق أمان كاملًا:** يلزم لاحقًا ضبط معدلات الطلبات ومكافحة التسجيل الآلي والتحقق من البريد وسياسة نسخ احتياطية. ابدأ بمجموعة محدودة موثوقة.
- وسائط `/media/:id` متاحة لمن يعرف رابطها؛ لا تعتبر هذه الواجهة مخزنًا سريًا لملفات حساسة أو تشفيرًا طرفيًا. بوتات تلغرام ليست تخزينًا مشفرًا من طرف إلى طرف.

## ما اختُبر وما بقي

```sh
npm ci --prefix server
node --test server/tests/*.test.js
```

تغطي الاختبارات فشل الإعداد الآمن، فحص البوت والوجهة، منع القنوات العامة، رفع/تنزيل الوسائط، إخفاء الأخطاء، الحجم والمهلة/منع التحويلات، وذاكرة مسار الملف. اختبار HTTP يشغّل الخادم الحقيقي في وضع الإنتاج مع PGlite معزولة ويحاكي Telegram فقط: يسجّل حسابًا، يرفع PNG بطلب multipart، يسترجع الصورة عبر `/media`، ويتحقق من منع الكتابة دون مصادقة ومنع تسريب التوكن عند فشل المزود.

لم يُبنَ Docker image داخل هذه الجلسة لعدم توفر Docker، ولم تُختبر استضافة Render حية أو بيانات Telegram حقيقية. الاختبارات لا تثبت الاتصال الفعلي ببوت المالك أو دفع الرسوم أو إتاحة التطبيق على هاتفه.
