# تحديث نبض داخل التطبيق (OTA)

## ما تم تنفيذه وما لم يُفعّل بعد

أُضيفت مكتبة `expo-updates`، وإعداد مشروع ديناميكي، وشارة عربية صغيرة للتنبيه والتنزيل والتثبيت، وزر **القائمة ← تحديث التطبيق**، ومسار نشر من GitHub إلى **EAS Update** بعد نجاح الفحوص.

**لا يكفي دمج الكود وحده لتفعيل الخدمة.** يلزم مشروع Expo حقيقي، وصلاحية نشر، وتثبيت APK تأسيسي بتهيئة ذلك المشروع. لا يوجد ID أو token تجريبي مُضمّن في التطبيق. إن لم يُضبط المشروع، تُعطّل OTA صراحةً وتعرض الشاشة أنها غير مفعّلة، وتُتخطى مهمة النشر.

هذا إشعار **داخل التطبيق** عند فتحه أو إعادته إلى الواجهة، وليس Push notification يصل والهاتف مغلق. تنطبق حدود استخدام وتكاليف EAS بحسب خطة الحساب؛ لا يفترض هذا التنفيذ خطة مجانية أو استخدامًا غير محدود.

## إعداد لمرة واحدة

1. رُبط المشروع العام الذي زوّد به صاحب التطبيق:
   - Project ID: `eec41206-1069-4604-aa2a-3fcc812f1ecd`، محفوظ في `mobile/app.json` وليس سرًا.
   - Expo slug: `fysbwk` بحسب أمر إعداد المشروع المرسل من Expo. اسم التطبيق الظاهر **نبض**، ومعرّف Android `app.nabd.social` لم يتغيّرا.
   - يجب أن يطابق slug في Expo هذه القيمة؛ EAS يرفض النشر إن اختلفا. لم نتحقق من بيانات حساب Expo الحية، لعدم توفر صلاحية النشر داخل بيئة التطوير.
   - لم تعد إضافة `EXPO_EAS_PROJECT_ID` إلى GitHub إلزامية؛ إن كانت موجودة فإنها تتجاوز المعرّف في الملف، ويجب أن تشير إلى المشروع الصحيح وتطابق slug. تغيير الربط يستلزم APK جديدًا.
2. في GitHub، من إعدادات مستودع `f0uri/Nabd` ثم **Secrets and variables → Actions**:
   - في **Secrets**: أضف `EXPO_TOKEN` من حساب Expo المخوّل بالنشر إلى هذا المشروع. **لا تضعه في Variables أو ملفات التطبيق أو المحادثة أو EXPO_PUBLIC_***.
   - في **Variables**: أضف `NABD_API_URL` بعنوان GraphQL العام الآمن للخادم، مثل `https://YOUR_REAL_HOST/graphql`. لا تستخدم localhost على هاتف حقيقي.
   - في **Variables**: يُنصح بضبط `NABD_DATA_SOURCE=graphql` للنسخة المتصلة بالخادم. إن لم يُضبط، يبقى سلوك `auto` السابق دون تغيير؛ إصلاح سلوك Mock ليس جزءًا من هذا التغيير.
   - صلاحية اتصال GitHub في جلسة التطوير سمحت بنشر الكود، لكنها أعادت 403 عند الوصول إلى إعدادات Variables وSecrets؛ لم نضف أيًا منها نيابة عن صاحب المستودع.
3. مسار النشر ينشئ قناة `production` وفرعها تلقائيًا إن لم تكن القناة موجودة. يفحص جميع صفحات القنوات أولًا؛ أي خطأ في تسجيل الدخول أو الاتصال يوقف النشر ولا يُعامل كأن القناة مفقودة. لا يعدّل ربط قناة موجودة.

   للإنشاء اليدوي الاختياري، داخل `mobile/` من جهاز موثوق عليه Node 22 وبعد تسجيل الدخول للحساب الصحيح:

   ```sh
   npx eas-cli@27.2.0 login
   npx eas-cli@27.2.0 project:info
   # للإنشاء الأول فقط: ينشئ/يعيد استخدام فرع بنفس الاسم ويربطه بالقناة الجديدة.
   npx eas-cli@27.2.0 channel:create production
   ```

   لا يستخدم `channel:create` الخيار `--branch` في النسخة المثبتة من CLI. إذا كانت القناة موجودة، راجع ربطها بدل إعادة إنشائها.
4. بعد دمج تغييرات الربط في `main` وضبط متغيرات الخادم، شغّل **Android APK** ونزّل وثبّت هذا APK مرة واحدة على الأجهزة. النسخ السابقة لا تستقبل تحديثات هذا المشروع ما لم تحتوِ الوحدة الأصلية والتهيئة الصحيحتين.
5. أضف `EXPO_TOKEN`، ثم شغّل **App updates (OTA)** على `main` لنشر التحديث الأول. بعد ذلك، تغييرات `mobile/**` المدمجة في `main` تنشر تلقائيًا بعد نجاح الفحوص. طلبات الدمج تُفحص فقط ولا تنشر أو تحصل على مفتاح النشر. وجود معرّف مشروع مرتبط دون token يوقف مهمة النشر برسالة واضحة، ولا يعني أن OTA مفعّلة للمستخدمين.

يمكن استخدام EAS Build بدل GitHub لبناء APK؛ ملف `eas.json` يحتوي profile `production` مع القناة نفسها. يجب توفير المعرّف ومتغيرات التطبيق العامة نفسها لعملية البناء والنشر. إعداد التوقيع والإصدار مسؤولية صاحب التطبيق؛ البناء الحالي في GitHub ما زال نسخة اختبار موقعة بمفتاح الاختبار كما كان سابقًا، وليس إعداد متجر إنتاجي.

> إذا كان الكود يعمل في مساحة تطوير لا تسمح بالاتصال بخدمات Expo أو لا تملك EXPO_TOKEN، يمكن فحص الكود وتوليد Android فقط، وليس إنشاء مشروع حسابك أو إثبات نشر حي.

## ما يحدث عند المستخدم

- فحص أول بعد فتح التطبيق بثلاث ثوانٍ، وفحص عند العودة من الخلفية، بحد أقصى فحص تلقائي كل 15 دقيقة أثناء العملية. زر الفحص اليدوي يتجاوز المهلة.
- عند توفر تحديث متوافق تظهر شارة صغيرة **متوفر تحديث**، بلا Modal أو تعتيم أو بيانات تقنية. الضغط عليها يبدأ التنزيل، ويمكن إخفاؤها بزر الإغلاق. لا يبدأ التنزيل لمجرد ظهورها.
- بعد التنزيل تصبح الشارة **تثبيت التحديث**، ووصفها الصوتي يوضح إعادة تشغيل التطبيق. الضغط على التثبيت إجراء مستقل، ليختار المستخدم الوقت المناسب لحفظ مسوداته.
- إذا أخفى المستخدم الشارة بعد اكتمال التنزيل، قد تُحمَّل النسخة المنزّلة في الفتح البارد التالي للتطبيق؛ هذا سلوك تحميل التحديثات المخزنة في Expo Updates.
- عند انقطاع الشبكة أثناء الفحص التلقائي لا تظهر نافذة خطأ مزعجة. عند فشل التنزيل تبقى النسخة الحالية ويظهر خيار إعادة المحاولة.
- لا تُغيَّر توكنات المستخدم أو بيانات حسابه ولا يُجرى حذف لـ AsyncStorage من نظام التحديث. لكن المسودات الموجودة في الذاكرة قد تضيع عند إعادة التشغيل، لذلك لا تُفرض إعادة التشغيل فور التنزيل.
- لا توجد نسبة تقدم مصطنعة؛ يُعرض مؤشر انتظار أثناء التنزيل.

## التوافق والتغييرات الأصلية

نستخدم `runtimeVersion: { policy: 'fingerprint' }` وقناة `production` مثبتة داخل إعداد Android. بصمة runtime تمنع وصول JavaScript يتطلب مكتبات أو إعدادات أصلية غير موجودة في APK المستخدم. مجلدا `android` و`ios` المولدان غير متتبعين، وتبقى حسابات البصمة في وضع CNG/managed.

- تغييرات الواجهات ومنطق JS والأصول يمكن نشرها OTA إذا بقي runtime متوافقًا.
- إضافة مكتبة أصلية أو صلاحية أو تغيير إعداد أصلي يتطلب **APK جديدًا**. قد تنتج بعض تغييرات الإعدادات/الأدوات بصمة جديدة أيضًا؛ اختيار محافظ أفضل من تحميل كود غير متوافق.
- تغيير project ID أو قناة التحديث داخل JS لا يعيد تهيئة APK قديم؛ يحتاج بناءً أصليًا جديدًا.
- تغييرات الخادم تُنشر على استضافة الخادم بصورة مستقلة، ولا يحوّل هذا التنفيذ GitHub إلى استضافة للخادم.
- رسالة «أحدث تحديث متوافق» لا تعني أن الجهاز يملك أحدث APK إن تغيّر runtime.

## الأمان والاسترجاع

- النشر على `main` فقط، بعد TypeScript واختبارات التحديث والتنقل وتصدير Android JS. يمكن لصاحب المستودع إضافة حماية/موافقة نشر إلى GitHub إذا احتاج مرحلة إصدار يدوية.
- `EXPO_TOKEN` يُستخدم داخل مهمة النشر فقط، وليس داخل APK أو بيانات المستخدم. صلاحية EAS هي التي تسمح برفع كود تنفيذي للمستخدمين؛ احمِ الحساب والمستودع واستعمل المصادقة الثنائية.
- endpoint المثبت يستخدم HTTPS لخدمة EAS. **لم يُضف توقيع manifests بشهادة مملوكة للمشروع**؛ إن أُريد Expo Update Code Signing، فيجب إعداد الشهادة ومفتاح التوقيع بصورة مستقلة وبناء APK يحتوي الشهادة قبل الاعتماد عليها.
- تبقى النسخة المضمّنة وسياسات الحماية الافتراضية في Expo مفعلة، بما فيها `ON_ERROR_RECOVERY`. لا نضبط `disableAntiBrickingMeasures`. الاسترجاع التلقائي الأصلي يدعم حالات معينة وليس ضمانًا ضد كل أخطاء التطبيق.
- لتراجع إداري عن إصدار، استخدم أوامر EAS المدعومة من حساب موثوق، مثل `eas update:republish` أو `eas update:roll-back-to-embedded` بعد مراجعة `--help` وتحديد القناة/runtime الصحيحين. يتعامل التطبيق كذلك مع تعليمات الرجوع إلى النسخة المضمّنة ويطلب الموافقة قبل إعادة التشغيل.
- لا توجد وظيفة تنزيل APK عشوائي من رابط أو تثبيت Android صامت في هذا التنفيذ.

## الاختبارات

```sh
cd mobile
npm ci
npm run typecheck
npm run test:updates
npm run test:navigation
npx expo export --platform android
```

تغطي اختبارات تهيئة القناة البحث بالصفحات والإنشاء عند الغياب وعدم تعديل القنوات الموجودة وإيقاف النشر عند أخطاء الخدمة أو الإنشاء.

الاختبارات تحاكي adapter الخاص بـ Expo لتغطية الفحص والتأجيل والتنزيل والموافقة على إعادة التشغيل، والفشل وانقطاع الشبكة ومنع الطلبات المتزامنة، وrollback، وتعطيل الخدمة عند عدم ربط المشروع. كذلك اختُبر توليد Android ببيانات project ID اصطناعية، وفُحص تطابق fingerprint قبل prebuild وبعده. المعرفات الاصطناعية في الاختبارات لا تُستخدم لرفع إصدار حقيقي.

التحقق النهائي بعد الإعداد يحتاج جهاز Android فعليًا: تثبيت APK التأسيسي، نشر تعديل JS صغير، التأكد من ظهور التنبيه، تنزيله وتطبيقه، اختبار وضع الطيران، ثم نشر تغيير أصلي للتأكد من عدم وصوله إلى runtime القديم. لم يُجرَ هذا الاختبار الحي بعد.

## إذا كيبان «أحدث نسخة» والتحديث ما وصلش

نجاح نشر OTA ما كيثبتش توافقه مع APK المثبت. تم توثيق اختلاف فعلي بين fingerprint داخل APK وبصمة النشر، وإضافة تثبيت البصمة قبل Gradle والتحقق من **APK نفسه** قبل رفعه. راجع [الفحص المعمق ونتائجه وخطوة APK لمرة واحدة](deployment-audit.md). لا تبدل runtime إلى بصمة قديمة يدويًا ولا تمسح بيانات التطبيق كحل عام.

## أيقونة نبض الحمراء المرسلة من صاحب التطبيق

- الصورة الأصلية استُخدمت دون إعادة رسم: `mobile/assets/icon.png` نسخة RGB معتمة بقياس 1024×1024، و`mobile/assets/adaptive-icon.png` طبقة شفافة مع الشعار كاملاً في الوسط وهوامش لحماية الكتابة والإطار من أقنعة Android.
- رُبطت الأيقونة في إعداد Expo العام وAndroid adaptive icon بخلفية بيضاء؛ لم يتغير اسم الحزمة أو هوية مشروع Expo أو قناة التحديث.
- تظهر الصورة المحلية في شاشة الدخول، دون اتصال بخادم أو تلغرام. أُزيلت لاحقاً من رأس التطبيق بطلب صاحب التطبيق، وبقي اسم نبض وأيقونة الهاتف كما هما. بقيت الألوان والتنقل وبيانات الحسابات كما هي.
- **هذا الإصدار يغيّر إعداداً أصلياً:** أيقونة شاشة الهاتف تحتاج تنزيل APK الجديد وتثبيته فوق النسخة الحالية. نشر OTA وحده لا يغيّر أيقونة Android/iOS، وتغيّر البصمة يمنع وصول هذا الإصدار إلى APK ذي runtime قديم، حتى لشعاره الداخلي. لا نمسح البيانات ولا نتجاوز فحص التوافق لجعل الأيقونة تبدو كتحديث OTA.
- بعد تثبيت APK الجديد، يمكن استقبال التغييرات اللاحقة المتوافقة عبر OTA بالطريقة المعتادة. لا يعد نجاح التصدير أو النشر وحده إثباتاً على وصول الأيقونة إلى هاتف فعلي.

## تبسيط الواجهة بعد تأكيد وصول OTA

بطلب صريح لاحق من صاحب التطبيق، أُزيلت شاشة تحذير تلغرام كذلك، وأصبح الاتصال وقراءة النسخة المثبتة تلقائياً. لا تتم تهيئة بيانات جديدة إلا بتأكيد منفصل، والأخطاء الحقيقية تبقى مختصرة وقابلة لإعادة المحاولة. استُبدلت نافذة التحديث بشارة صغيرة؛ لا تظهر بيانات Runtime/Channel/Source/Update ولا زر التفاصيل في الواجهة، مع بقاء بيانات التشخيص في المتجر البرمجي. لم تتغير فحوص التوافق أو إعدادات أيقونة الهاتف أو native dependencies.
